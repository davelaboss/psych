IMPLEMENTATION
An operator-only procedure appends ownerRetention to the existing authoritative
order snapshot and appends an OWNER_RETENTION event to the existing fulfillment
audit. The marker states that David and Maria retained the four exact units,
with zero actual cash received/refunded and no customer sale or physical delivery.
It references the original payment c5929d87-e991-41bb-a468-2ddca8605c6d,
adjustment 375c0bab-e233-45c2-ad12-2ecb8db53a55 and PREPARE event 204.
No original payment, adjustment, receipt, order field or previous audit record is
deleted, zeroed, voided or overwritten. The original financial entries remain
historical evidence. The original order status is also preserved for history;
the explicit non-sale marker governs operational classification and reporting.

Batch 0d646d9f-80ae-4db5-acd6-bce66eca410a moves only from PREPARED revision 2
to CLOSED_OWNER_WITHDRAWAL revision 3. delivered_at stays null, auto_attach stays
false, all memberships remain, and no DELIVER event or payment exception is
created. Closed batches cannot be reopened, delivered, combined or separated.
Automatic assignment excludes the corrected order even if membership evidence
were later missing. Closed history stays available under Todos, with no delivery
controls, and is excluded from outstanding preparation/delivery filters.

Inventory capacities, committed counters, reservations, product IDs, source
information and photographs remain unchanged. Committed physical stock remains
unavailable. A read-only projection derives retained quantity from the exact
order-line marker and subtracts only those units from customer-sale counts.
043/411/432 become UNLISTED / NO LONGER FOR SALE, with zero customer units sold.
466 remains AVAILABLE with one owner-retained unit, the other customer's one
committed unit and one free unit. Future legitimate purchases of the free unit
retain the existing checkout/price/locking rules. Liquidation logic is untouched.

Admin statistics and Sale Pulse exclude this owner record from customer sales.
Admin and private-order views label it personal retention and explain that the
original 95,000 PYG payment and matching adjustment are historical entries, not
cash exchanged. Normal payment/receipt/ledger/pickup mutations reject this closed
record. Genuine customer full-payment recognition, refunds, partial payments,
credits and exceptions retain their existing policy. No customer protection is
relaxed. OWNER/REVIEWER authentication is unchanged; no new HTTP correction action
or Admin write control is introduced.

SCHEMA
20261118_historical_owner_retention.sql extends the existing batch-status and
audit-event CHECK constraints with the new non-delivery values. It adds guards
against editing/removing retained order history, closed batch/membership and the
new audit evidence, including bulk truncation. It performs no historical update
or backfill. Applying this migration alone does not execute the correction.
Old deployed code can coexist with the empty schema extension, but the new
reader/guard code must be published before any future historical execution.
After execution, rollback must retain the new non-sale reader/guard behavior;
reverting to old readers would mislabel preserved history as an ordinary sale.
No routine undo/reopen feature is added. Any later change needs a separately
reviewed append-only correction, not deletion of this evidence.
