PICKUP SELECTIVE CONTAINMENT — PROPOSED OPERATING PROCEDURE
Development preparation only. No production activation, migration, hosting change,
publication, or publishing unlock has been performed for this change.

MECHANISM AND ALTERNATIVES
One PostgreSQL singleton controls explicit pickup mutations and Item-payment
allocation/exception mutations. Existing Admin authentication is reused. Two
additive tables hold current state and append-only audit events. Initial state is
PAUSED. Every target write takes FOR SHARE on the singleton as its first lock,
inside the existing transaction; changing state takes FOR UPDATE and commits its
audit event atomically. No cached flag or deployment-time environment flag is used.

An environment flag needs a new deploy and cannot drain existing transactions.
Calendar blackouts do not stop payment decisions or direct appointment mutations.
Blocking the entire live site would stop purchasing. Reverting to an older build
would restore unguarded scheduling. A database switch is the smallest runtime
mechanism that coordinates these writers without a new authentication system.

COVERAGE
- New customer/Admin bookings, reschedules, Item-membership replacements,
  explicit Admin appointment cancellations, and same-slot POST retries.
- ALLOCATE, REVERSE, REQUIREMENT and REVOKE, including idempotent POST retries.
- Both /api/orders/pickup and /.netlify/functions/customer-pickup.
- Both /api/admin/pickup and /.netlify/functions/admin-pickup.
- Both /api/admin/item-payment and /.netlify/functions/admin-item-payment.
- The authoritative shared transaction functions also enforce the pause.

The switch does not change orders, payments, ledger decisions, appointments,
reservations, inventory, prices or seller notifications. Only control state and
its audit event change. GET views remain available; scheduling controls disappear,
existing appointments remain visible, and financial eligibility stays distinct
from the temporary operational pause. Missing control state/read failure rejects
target writes and hides write controls. Recovery does not replay rejected requests.

BOUNDARY: this pauses explicit pickup/payment-decision operations, not the whole
order lifecycle. Payment confirmations, receipts, ordinary order cancellation,
expired-reservation renewal, fulfillment, calendar-blackout management and existing
notification dispatch retain their established behavior. In particular, existing
order cancellation/renewal safeguards can clear an appointment as before. Pausing
itself never cancels an appointment. This is not a database-wide appointment freeze
and does not grant permission for any historical correction.

While activation is pending, earlier/newly admitted shared-lock writers can finish.
Acknowledged pause means all earlier guarded writer transactions have committed or
rolled back, and subsequent guarded mutations are rejected with HTTP 503. No running
transaction is killed. A five-second lock timeout rolls back the control request
and returns 409: pause NOT confirmed. A dropped HTTP response is also uncertain.
Always refresh state/history before retrying. Do not assume a timeout means active
containment or blindly send a stale resume. Failed reads are not confirmation.

Concurrent controls use expectedRevision; only one can win a revision. Request UUIDs
make identical retries idempotent. An old successful resume retried after a newer
pause returns CURRENT paused state and never overwrites it. Reusing a UUID with a
different payload fails. State/event writes are atomic; events reject edit/delete/
truncate, and the singleton rejects delete/truncate. Actor is existing ADMIN, not
a newly introduced identity service; the owner is the sole Admin.

API ALTERNATIVE
Existing Admin header x-admin-token; same authentication for alias and direct path.
GET /api/admin/pickup-containment returns state plus ten most recent audit entries.
POST /api/admin/pickup-containment (or /.netlify/functions/admin-pickup-containment):
{"id":"<fresh UUID>","paused":true,"expectedRevision":<GET revision>,"reason":"<incident reference>"}
HTTP 200 returns state and event AFTER COMMIT. Check state.paused, not merely ok.
Use paused:false only for an approved recovery. Preserve exact request UUID/payload
if reconciling an uncertain response; a refresh may reveal a later control event.
The full append-only history remains in pickup_write_control_events; older evidence
can be retrieved with authorized read-only database access, without editing records.
