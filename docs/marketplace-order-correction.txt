IMPLEMENTATION

Authenticated endpoint: /.netlify/functions/admin-correct-marketplace-order
GET: read-only plan; does not call getOrder, repair Blobs, or renew holds.
POST: fixed action, fixed order, fixed products and fixed Gs. 30,000 amount.
No general-purpose item, price, payment or inventory editing input exists.

The write uses existing inventoryTransaction and orderLock. Under the same
order/product locks it validates version 2, the original four prices and
quantities, one pending receipt, no payment/commitment, four protected ORDER
holds, capacity one/committed zero, and no pickup, fulfillment or item-payment
decision. Changed state aborts with 409; there is no adaptation to paid orders.

It saves original details (including buyer, receipt and pending payment
history, excluding the access-token hash) in order_snapshot.orderCorrections.
The live order keeps its original identity, buyer, receipt, token hash and
checkout fingerprint. An ORDER_CORRECTION entry in the existing paymentNotes
history records the reason and authorization reference for Admin review.
This uses the existing durable JSON snapshot; no new audit table is needed.

Only the three removed ORDER reservations are deleted. Capacity is never
increased. The retained line receives its order-specific Gs. 30,000 price;
its obsolete liquidation annotation is removed only from the active order
line and remains in the original audit snapshot.

The existing confirmation implementation is extracted into a locked helper,
which the routine confirmation wrapper still calls with notifications on.
The correction calls that same helper with notifications off, confirming the
existing pending payment as FULL/ADMIN_VERIFIED and committing only Item 369.
There is one atomic snapshot write and one projection-version increment.
Any failure rolls back the reservation release, payment, commitment and audit.
The resulting status is PAYMENT_CONFIRMED, never PICKED_UP/ENTREGADO.

The endpoint then uses existing recoverOrderBlob/synchronizeOrderProjection.
If Blob synchronization fails after SQL commit, it returns 503/committed:true.
An exact POST retry recognizes the fixed correction ID, makes no second
financial/inventory change, and repairs the Blob projection. Never recreate
the order or reverse inventory to recover from projection failure.
No notification is queued, replayed, drained or sent by this endpoint.
